# Decision Register — Fast-AtomRAG Core

Evidence levels: **L1** вывод из требований · **L2** свойство технологии + механизм · **L3** документация/статья · **L4** измерено в этом репозитории (`bench/`, `tests/`).

## Требования и допущения

| ID | Требование / допущение | Статус |
|---|---|---|
| R1 | Retrieval-фаза (анализ + эмбеддинг + поиск + граф) укладывается в малую долю SLA 2 c, чтобы бюджет остался LLM-генерации | Цель: p95 ≤ 50 мс при 100k атомов |
| R2 | Атомы переживают рестарт, upsert идемпотентен по `atom_id` | Обязательно |
| R3 | Мультихоп: атом во 2-м хопе от сущности запроса должен находиться, даже если лексически далёк | Обязательно |
| A1 | Масштаб MVP ≤ 100k атомов, одна нода | ASSUMPTION — при ложности рушится ADR-002 (exact search) |
| A2 | Нагрузка — единицы/десятки RPS, писатель один | ASSUMPTION — при ложности рушится ADR-001 (один процесс) |
| A3 | Латентность/стоимость бандлов и приоры качества в роутере | ASSUMPTION (из исследовательских заметок, L1) — ADR-003 |
| A4 | Сервис внутренний; запись защищена API-ключом, чтение открыто | ASSUMPTION — при публичном доступе нужен auth на чтение + rate limit |

**Вне скоупа:** LLM-генерация, извлечение атомов из документов, обучение классификатора сложности.

## Architecture Budget

| Ресурс | Лимит | Использовано |
|---|---|---|
| Сервисы | 1 | 1 (модульный монолит) |
| Хранилища | 1 | 1 (SQLite-файл) |
| Брокеры | 0 | 0 |
| Внешние runtime-зависимости | ≤ 6 | 5 (fastapi, uvicorn, pydantic, prometheus-client, numpy) |

Из исходного прототипа удалены: `usearch`, `networkx`, `onnxruntime`, `httpx` (runtime). Причины — ниже.

## ADR-001 — Модульный монолит, один процесс владеет индексом
- **Decision:** Domain (stdlib) ← Application (use cases, порты) ← Infrastructure (SQLite, numpy) ; Presentation (FastAPI). `uvicorn --workers 1`.
- **Why:** индекс и граф живут в памяти процесса. В прототипе `--workers 2` давал два независимых индекса: `POST /atoms` попадал в один воркер, поиск — в другой (L1: каждый процесс uvicorn имеет свою память).
- **Trade-off:** вертикальный потолок одного ядра на запрос; чтения сериализуются `RLock`.
- **Exit:** read-реплики, каждая строит индекс из общего снапшота SQLite; запись — через один writer.
- **Status:** ACCEPTED.

## ADR-002 — Exact cosine на numpy вместо HNSW (usearch)
- **Decision:** `ExactVectorIndex` — непрерывная float32-матрица, `matmul` + `argpartition`; порт `VectorIndex`.
- **Why:** точный поиск, ноль внешних нативных зависимостей. **L4 (итерация 2):** p95 total (vector) = 2.2 мс @10k, 24.6 мс @100k атомов, dim 512, 1 vCPU.
- **Alternatives:** usearch/FAISS HNSW — отложено: при A1 выигрыш < бюджета, плюс recall < 100% и сложность upsert/delete.
- **Trigger на замену:** p95 vector-фазы > 30 мс на целевом железе или > ~150k атомов → адаптер HNSW за тем же портом.
- **Status:** ACCEPTED.

## ADR-003 — Роутер CA-RAG: функция полезности + эвристика сложности
- **Decision:** `U_b = wQ·Q̂_b − wL·L_b/L_ref − wC·C_b/C_ref`, бандлы с `L_b > SLA` исключаются; если не подходит ни один — самый быстрый с `sla_feasible=false` (graceful degradation). Сложность (0/1/2) — структурная эвристика (подзапросы, найденные сущности, длина).
- **Evidence:** формула — L3 (CA-RAG в заметках); числа `L_b`, `C_b`, `Q̂_b` — **ASSUMPTION/UNVERIFIED**.
- **Validation plan:** логировать (запрос, бандл, исход) → разметка по Adaptive-RAG → TF-IDF+линейный классификатор → заменить `complexity_level` и таблицу приоров. Режим `auto` — opt-in, по умолчанию `graph`.
- **Status:** ACCEPTED (experimental).

## ADR-004 — Fusion по умолчанию RRF, а не линейная формула
- **Decision:** `S = α/(k0+rank_cos) + (1−α)/(k0+rank_ppr)`, `k0=60`; линейная формула доступна через `ATOMRAG_FUSION=linear`.
- **Why (L4):** `tests/test_service.py::test_graph_mode_surfaces_second_hop_atom...` — при линейном слиянии атом второго хопа (PPR-масса 0.13 против 0.33) проигрывает лексическим дистракторам с cos≈0.69; RRF его поднимает. Линейная формула нарушает R3.
- **Trade-off:** `score` теряет абсолютный смысл; в ответе отдаются сырые `vector_score` и `graph_score`.
- **Status:** ACCEPTED.

## ADR-005 — Локальный PPR (forward push) вместо `networkx.pagerank`
- **Decision:** алгоритм Andersen–Chung–Lang по двудольному графу атом↔сущность, кандидаты = top-K по массе атомов ∪ vector top-K.
- **Why:** `nx.pagerank` с personalization — степенной метод по **всему** графу, O(E·iter) на каждый запрос (L2). Push трогает только окрестность сидов; работа ограничена `eps` и `max_pushes`. **L4 (итерация 2):** graph-фаза p95 = 5.5 мс @10k, 5.6 мс @100k (практически не растёт с размером графа).
- **Correctness:** сверка с power iteration до 1e-6 (`test_push_ppr_matches_power_iteration`).
- **Status:** ACCEPTED.

## ADR-006 — Детерминированный hashing-эмбеддер вместо ONNX MiniLM
- **Decision:** signed feature hashing слов и символьных 3–5-грамм, `blake2b`, dim 512.
- **Why:** прототип строил input_ids через `hash(token) % 30522` — это не словарь модели, а `hash()` рандомизирован по процессам (PYTHONHASHSEED) → разные векторы в разных воркерах/после рестарта. Fallback без модели был `np.random` — семантически пустой. Hashing-эмбеддер детерминирован (L4: `test_embedder_is_stable_across_processes`), даёт лексическое сходство с частичной устойчивостью к русской морфологии.
- **Trade-off:** нет синонимии/парафраза. Пропускная способность **L4:** ~1.8k атомов/с на 1 vCPU (первичная индексация 100k ≈ 1 мин; рестарт грузит готовые векторы: 4.1–6.8 с на 100k в разных прогонах).
- **Exit:** адаптер `Embedder` для ONNX с настоящим токенайзером; смена `embedder_id` автоматически переэмбеддит базу при старте (`test_embedder_change_triggers_reembedding_on_load`).
- **Status:** ACCEPTED.

## ADR-007 — SQLite как единственный источник истины
- **Decision:** таблица `atoms(atom_id PK, text, entities JSON, embedder_id, vector BLOB)`, WAL, `PRAGMA user_version` для схемы; индекс и граф — производные, строятся при старте.
- **Why:** R2 при A1/A2 без отдельного сервера БД. Запись: сначала SQLite (commit), потом память — под одним lock.
- **Blast radius:** диск недоступен → upsert отдаёт 500, память не меняется; поиск продолжает работать. Схема новее кода → отказ старта (fail-closed).
- **Backup:** `sqlite3 atoms.db ".backup atoms.bak"` (онлайн-бэкап работает при WAL). Восстановление = заменить файл и перезапустить.
- **Status:** ACCEPTED.

## ADR-008 — Нормализация сущностей: stdlib-стемминг + trigram-fallback
- **Decision:** ключ сущности = `stemmed_key`: NFKC → casefold → `ё→е` → дефисы/подчёркивания/слэши в пробел → токены → Snowball-Russian или Porter-English на каждый токен (токены с цифрами и ≤2 символов не трогаются). Одна функция строит и ключи графа, и разбор запроса. Если точного совпадения нет — char-3gram Jaccard ≥ 0.75 по названиям сущностей с prefix-filtering (пробуются только самые редкие `|A| − ⌈0.75·|A|⌉ + 1` грамм окна; любая подходящая сущность обязана делить хотя бы одну).
- **Why:** «коллапса маршрутизатора» и «коллапс маршрутизатора» были разными узлами; мультихоп рвался, если сущность записана в разных падежах в соседних атомах.
- **Budget:** 0 новых зависимостей (`re`, `functools.lru_cache`, `unicodedata`).
- **Evidence (L4):** эталонные выходы алгоритмов в `tests/test_text.py` (relational→relat, generalization→gener, бегавшись→бега, красивейший→красив…). Оверхед seeds-фазы p95: **0.106–0.163 мс** (10k/100k атомов, `bench_retrieval.py`), тест-бюджет `< 0.2 мс` на медиане.
- **Trade-off:** стемминг ≠ лемматизация: возможны редкие склейки разных слов в одну основу (overstemming) и пропуск супплетивных форм. Порог 0.75 консервативный: «kubernetis»→«kubernetes» (Jaccard 0.70) не ловится намеренно.
- **Миграция:** ключи не хранятся в БД (только отображаемые имена), граф пересобирается при старте → смена нормализатора не требует миграции. Откат: `ATOMRAG_ENTITY_STEMMING=false`, `ATOMRAG_FUZZY_THRESHOLD=0`.
- **Status:** ACCEPTED.

## ADR-009 — Самокалибровка роутера по реальной телеметрии
- **Decision:** `LatencyTracker`: по `deque(maxlen=256)` на режим retrieval (`none`/`vector`/`graph`; `graph` — это гибрид vector+PPR). Пишется фактическая длительность `search()` для выполненного режима. Пока в окне `< 10` замеров — консервативный дефолт (vector 50 мс, graph 100 мс); после — скользящий p95. Роутер считает `L_b = generation_s(b) + retrieval_p95(mode(b))` и отсекает планы с `L_b > SLA`; если не прошёл ни один — самый быстрый план + счётчик `sla_fallbacks`.
- **Exposure:** `/health/ready → router.modes.{mode}.{p50_ms,p95_ms,sample_count,calibrated}, router.sla_fallbacks`; Prometheus `atomrag_retrieval_p50_seconds`, `atomrag_retrieval_p95_seconds`, `atomrag_retrieval_samples`, `atomrag_router_sla_fallbacks`.
- **Evidence (L4):** `tests/test_calibration.py` — p95 graph 0.5 c → `b3_graph_k5` (1.6 + 0.5 > 2.0 c) выбывает, запрос уходит в vector-бандл; ограниченность окна; счётчик fallback.
- **Остаётся UNVERIFIED:** `generation_s` — LLM работает вне сервиса и здесь не наблюдается. Это составляет ~95% `L_b`, поэтому калибровка закрывает только retrieval-часть. Следующий шаг — endpoint обратной связи от генератора (фактическая латентность + качество ответа) в тот же трекер.
- **Status:** ACCEPTED.

## ADR-010 — Атомарность SQLite ↔ in-memory
- **Decision:**
  1. При каждом подключении: `journal_mode=WAL` (старт падает, если WAL не включился на файловой БД), `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`; проверяется тестом `test_connection_pragmas`.
  2. Порядок записи под одним `threading.RLock`: валидация атома и вектора → транзакция SQLite (`with conn`: COMMIT или ROLLBACK) → мутация индекса/графа. Любая `sqlite3.Error` переводится в `StorageError` (HTTP 503), память не трогается.
  3. Если мутация памяти упала **после** commit (теоретически: MemoryError) — сервис помечается not ready, `/health/ready` отдаёт 503, оркестратор перезапускает, память строится из SQLite. Fail-closed вместо тихого расхождения.
  4. Re-upsert сначала удаляет все рёбра атома, затем добавляет новые; осиротевшие сущности удаляются вместе с trigram-индексом.
- **Почему `threading`, а не `asyncio.Lock`:** хендлеры синхронные и исполняются в threadpool FastAPI; `asyncio.Lock` не защищает код в разных потоках.
- **Evidence (L4):** `tests/test_consistency.py` — отказ диска на upsert/delete (память неизменна), сбой после commit → not ready → `load()` восстанавливает, повторный upsert с новыми сущностями не оставляет фантомных рёбер (проверено прямым PPR от старой сущности) и переживает рестарт.
- **Status:** ACCEPTED.

## Recall на стресс-корпусе (L4)
Корпус `bench/recall_corpus.py`: 66 атомов, 15 цепочек (9 двуххоповых, 6 трёххоповых; 10 RU, 5 EN), 30 дистракторов. Инварианты корпуса проверяются тестами: целевой атом не делит ни одной контентной основы с вопросом; соседние хопы пишут общую сущность в **разных** формах (plain-ключи не совпадают, стеммированные совпадают); у каждой цепочки один дистрактор связан со стартовой сущностью.

`python bench/eval_recall.py --repeat 20` (1 vCPU):

| variant | Recall@3 | Recall@5 | R@5 2-hop | R@5 3-hop | MRR@10 | chain R@5 | start-entity hit | p95 ms |
|---|---|---|---|---|---|---|---|---|
| vector_only | 0.000 | 0.000 | 0.000 | 0.000 | 0.016 | 0.000 | n/a | 0.57 |
| linear_fusion | 0.000 | 0.533 | 0.889 | 0.000 | 0.156 | 0.533 | 1.000 | 0.85 |
| rrf_hybrid_nostem | 0.000 | 0.000 | 0.000 | 0.000 | 0.016 | 0.000 | 0.200 | 0.57 |
| rrf_hybrid_stem | **0.733** | **1.000** | **1.000** | **1.000** | **0.322** | **1.000** | **1.000** | 0.79 |

Выводы и оговорки:
- Без стемминга граф бесполезен на этом корпусе: стартовая сущность находится в 3 из 15 вопросов, цепочки разорваны падежами.
- Линейное слияние тянет 2-hop (0.889), но не доходит до 3-го хопа (0.000).
- MRR 0.32: целевой атом обычно на 3-й позиции после атома первого хопа и связанного дистрактора. Для генератора это нормально (нужна вся цепочка, chain R@5 = 1.0), для «ответ = первый результат» — нет.
- **Ограничение валидности:** корпус написан вручную под проверку механизма и мал (15 запросов). Это L4 для механизма мультихопа и падежей, **не** оценка качества на реальных данных.

## Data Physics
- **Мутации:** сериализованы `RLock` сервиса; upsert идемпотентен (`ON CONFLICT DO UPDATE`), повтор безопасен.
- **Консистентность:** SQLite ACID; память обновляется только после commit (ADR-010). Падение процесса между ними → при рестарте память строится из SQLite.
- **Backpressure:** threadpool FastAPI (sync-хендлеры), лимиты размера тела в схемах (query ≤ 1000, text ≤ 4000, ≤ 32 сущностей), PPR ограничен `max_pushes`.

## Evolution Path
- **1×** (≤100k, единицы RPS): как есть.
- **10×** (~1M атомов): первый bottleneck — exact matmul (~250 мс экстраполяция L1) и RAM (1M×512×4 B ≈ 2 ГБ) → HNSW-адаптер + float16; второй — сериализация чтений → RW-lock/копирование при записи.
- **100×:** шардирование по сущностным кластерам, отдельный writer + read-реплики, внешний векторный движок за портом `VectorIndex`. Domain не переписывается.
